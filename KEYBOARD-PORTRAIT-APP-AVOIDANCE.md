# Portrait app-event normalization experiment

User priority: portrait chat input-bar avoidance first, then full landscape keyboard visibility. Extra six-point bottom clearance is withdrawn. Landscape remains unchanged and unsupported by this portrait experiment.

## Why a new component

The SpringBoard layer transform in 0.1.10 changes only displayed keyboard geometry. Its logs cannot reveal which frame an app receives. The new opt-in experiment adds TWO separately built components: portrait-avoidance-experiment (SpringBoard with a narrow Scene ticket publisher) and keyboard-app-avoidance (application process real-event adapter). Existing dock/probe targets do not enable the publisher and cannot produce app input-bar correction alone.

## Implemented behavior, not device proof

- After verified 9:16 host/remote geometry, the SpringBoard component identifies the exact target bundle through the original host's `currentActivityApp.bundleIdentifier`, resolves that bundle with `LSApplicationProxy`, verifies the returned app identity and obtains its data-container URL. It writes schema-2 layout state atomically to that app's `Library/Caches/com.minis.floatingview.keyboard-layout.plist`; it never relies on SpringBoard's private Preferences path for app reads. Scene, bundle, geometry and timestamp are included; no message text is stored. Container lookup/write failures skip publication and are logged. Device permission and data-protection behavior still require verification.
- App-process injection is filtered by the UIKit class `UIApplication` (the original keyboard tweak uses the same class-based filter mechanism for `UIKeyboardImpl`); the adapter also skips SpringBoard and Preferences in code. This is a class-presence filter, not a `com.apple.UIKit` bundle identifier filter.
- The app component reads only `NSHomeDirectory()/Library/Caches/com.minis.floatingview.keyboard-layout.plist`; it requires schema 2, an exact main-bundle ID match, Scene identifier, unique foreground `UIWindowScene`, current key-window bounds, matching screen, upright portrait, local inner keyboard and a fresh ticket (120s). A nil notification object is allowed; if UIKit supplies one it must be the authenticated Scene's `UIScreen`. Any failure passes the real notification unchanged. Target-container writability/readability is not yet proven on a device.
- The application-process dylib uses the UIKit class filter `UIApplication` and skips SpringBoard/Preferences in code. This matches the original tweak's class-filtering style (`UIKeyboardImpl`), unlike the previous `Bundles=com.apple.UIKit` setting.
- Once a real keyboard notification hook is entered, one-time diagnostics report adapter install failures and the first failed event/ticket/Scene/frame guard without logging message text or input contents.
- The app component overrides the actual class of the default notification center only in its process, after checking both original selector ABIs. It forwards each existing `postNotificationName:object:userInfo:` or `postNotification:` exactly once. A thread-local guard prevents converting the same nested dispatch twice. Custom notification-center instances pass through unchanged.
- Only real will/did-show and will/did-change-frame keyboard events are considered. A measured full-width, bottom-docked native-canvas frame is relocated to the bottom of the matching app's verified Scene without changing key height. Initial offscreen begin frames use the same coordinate conversion. All unrelated userInfo entries (native animation duration/curve, locality and other payload) survive. Already-corrected frames, floating/split/undocked keyboards, hide events, landscape, other apps/scenes and changed geometry pass unchanged. This does not emit extra keyboard events or change the app's Scene size.
- Main-process fullscreen, ratio-off, outer mode and teardown revoke only the matching Scene's ticket. Removing an installed app component also requires restarting the target app; already injected code cannot be unloaded by replacing package files.

The intended outcome is for an app's own keyboard-frame handler to place its input bar and content area above the actual displayed keyboard. The original floatingView audit confirms its item-state machine can scale/move the whole floating item, while its visible show/hide observer is for floatingView's own search UI; it does NOT establish a generic third-party chat input inset. This experiment instead tries a per-Scene correction of the real event frame. No generic scroll-view inset or third-party widget is mutated. Apps using a different private layout-guide path may not respond. UIKit layout guides, first-event timing, on-device container access, hide behavior and WeChat response remain unverified. This is not yet a confirmed input-bar fix.

## Validation evidence available in source

The latest SpringBoard `.ips` is conclusive for the fullscreen failure: arm64e UUID `ad2343a6-fcb3-3bb8-902a-cc3c90b29c20` matches the shipped 0.1.14 main dylib; `SIGABRT` unwinds through `fvKDDropForHost` and the DWARF-matched source location is `FVKeyboardDock.inc:228`, where the layer snapshot loop called `objectAtIndex:` without passing `i`. The system `CFPrefsPlistSource synchronize` frame is not the direct tweak call. The source now passes the index, and the Drop callback does no ticket/cache I/O.

`FVKeyboardApp_2.log` proves the app receives local UIScreen keyboard notifications with raw end frames `(0,554,430,378)` and `(0,932,430,378)`, but its named hook reports the per-app ticket missing/unreadable, so no frame is mapped. The reader now uses a bounded `open/read` + plist parse path and logs separate open errno, read-size, parse, root-type and later authorization failures. This distinguishes RootHide/data-protection/path timing from geometry. The expected mapped end frame for a 430×764.4 target and a 378-point keyboard is `(0,386.4,430,378)`; no numerical height change is made until the ticket transport succeeds.

The fullscreen-transition report is not accompanied by a SpringBoard crash log or faulting stack in the uploaded files, so its cause is not proven. The bridge revocation code did contain a lifetime hazard (clearing associated-object retains before finishing with those pointers). It now copies the expected path/Scene/bundle/stamp into a retained work dictionary first, and the fullscreen layout path queues ticket I/O until after the callback while restoring only owned keyboard-layer geometry synchronously. A regression check covers both. This is a targeted safety mitigation, not evidence that the reported Safe Mode is fixed; the matching SpringBoard `.ips` is needed for attribution.



## Packaging boundary

The next test package must explicitly contain the main portrait-avoidance-experiment dylib under the existing SpringBoard/Preferences filter, plus the separate app-only dylib with the UIKit `UIApplication` class filter; the app implementation skips SpringBoard and Preferences. Do not inject FVIndependent.c's SpringBoard geometry code into all apps. This is still an experimental notification-frame adapter, not a confirmed input-bar repair. Restart target apps after installation.
